# Decision Log

One line per real decision: **what** we decided and **why**. When you present
this project, this file is your script — every choice you can defend is a choice
you understand. Add to it whenever we decide something. Newest at the bottom.

| # | Decision | Why |
|---|----------|-----|
| 1 | **Language: Python** | It's the language I already understand, which serves my "explain it myself" goal. C# deferred — I'd be learning a new language *and* a UI at once. |
| 2 | **Database: SQLite now, PostgreSQL later** | SQLite is built into Python, needs no server, fine for one shop. Move to Postgres only when multiple computers share one live database. Both are SQL, so the design transfers. |
| 3 | **Track stock by BATCH, not a single quantity number** | Medicines expire. The same product bought in January vs June are different lots with different expiry dates; we must tell them apart to warn about expiry and sell oldest-first. |
| 4 | **Freeze `unit_price` on each `sale_item`** | Prices change over time. A past receipt must show the price it was sold at, not today's price. So we copy the price into the sale line instead of reading it from `medicines` later. |
| 5 | ~~Store `total_amount` on `sales`~~ → **REVERSED (#16): do NOT store it; compute from `sale_items`** | Mother's own principle: "record each small event, compute the summaries." Price is already frozen per line, so the total can be summed honestly and can never drift. No monthly/weekly total is stored anywhere either — every report is computed from raw sales. |
| 6 | **`category` is plain text on `medicines`, not its own table (for now)** | Simpler to start and easier to explain. A separate `categories` table would prevent typos ("painkiller" vs "pain killer") and allow renaming in one place — we'll revisit if the category list grows or gets messy. |
| 7 | **Flag `is_active` instead of DELETING a medicine** | Old sales point to the medicine. If we deleted it, past receipts would reference a missing product. Hiding it (is_active = 0) keeps history intact. |
| 8 | **Dates stored as ISO text ("2026-08-19")** | SQLite has no real date type. ISO text sorts correctly (bigger date = bigger string) and SQLite's date functions understand it. Consistent format is the whole trick. |
| 9 | **Foreign keys turned ON in code every connection** | SQLite ignores foreign keys unless you run `PRAGMA foreign_keys = ON` per connection. We put that in one shared `get_connection()` helper so we can never forget it. |
| 10 | **Backups from day one, using SQLite's backup API** | I lost data before. A plain file copy can be corrupt mid-write; the backup API copies a safe, consistent snapshot. |
| 11 | **Scope grew: pharmacy → full small clinic** (added patients, employees, visits, prescriptions) | Mother's v2 wishlist: the clinic has patients, staff, and clinical visits, not just medicine sales. Added additively — the pharmacy tables were unchanged. `medicines` is the bridge between the pharmacy and clinical sides. |
| 12 | **Diagnosis & treatment live on `visits`, not `patients`** | A patient returns many times with different problems. On the patient, each new visit would overwrite the last; on the visit, each patient builds a real history. |
| 13 | **Employee `role` is a field, not four separate tables** | Doctor/nurse/pharmacy/lab share the same columns. One table with a `role` field is simpler to build, explain, and filter. |
| 14 | **"Lab" is just a staff role — no lab-results table (yet)** | Confirmed with mother: the lab doesn't produce stored results in this version. Revisit only if that changes. |
| 15 | ~~Visits are NOT linked to sales~~ → **REFINED (#19): a sale MAY link to a visit, but a visit is never forced to have one** | A patient can still be seen and buy nothing (visit, no sale). But giving medicine during a visit counts as selling, so a sale can point back to its visit via `sales.visit_id`. Optional and one-directional. |
| 16 | **Store `date_of_birth`, not age** | Age changes every year; a stored age silently goes stale. Store the birth date and compute age when needed. |
| 17 | **Added `unit` and `strength` to `medicines`** | `unit` = how we count/sell it (tablet/bottle) — each medicine declares its own, so we don't force weight on everything. `strength` = the label dose ("500mg"), optional and descriptive only; a bandage has none. |
| 18 | ~~Open: does giving medicine in a visit reduce stock?~~ → **ANSWERED (#19): yes — giving medicine IS a sale** | Confirmed with mother: giving medicine to a patient during a visit counts as selling it. So it goes through the normal sale path and will reduce stock like any sale (stock logic still to be built). |
| 19 | **Dropped `prescription_items`; added `sales.visit_id` instead** | Since giving medicine = selling it, recording both a prescription and a sale would be double-entry that can drift. One source of truth: the sale. A sale optionally points to its visit. To see what a patient was given: join visit → sale → sale_items. |
| 20 | **Stock uses auto-FEFO in code; a physical habit keeps the shelf in sync** | The database can't see which box a hand grabs, so it always sells soonest-expiry-first (`ORDER BY expiry_date`) and reality must match it. Chosen habit (to confirm with mother): keep a newly-received batch boxed until the current one runs out, so only ONE batch is ever open and the seller physically can't grab the wrong one. Alternative habit: rotate stock (new behind old). Code is identical either way; totals and money stay correct regardless — only batch-level expiry can drift, fixed by a periodic recount. |
| 21 | ~~Short-item policy: blanket "full lines only"~~ → **SUPERSEDED by #22 (per-medicine flag)** | Originally: a short line is always left off, never partial. Replaced because whether partial is OK depends on the medicine (see #22). |
| 22 | **Partial-sale allowed PER MEDICINE via `allow_partial_sale` flag** | Turns the short-item rule into DATA, not a hardcoded global (fits the "keep shop-specific data as data" principle — a UI checkbox later just edits this column). When a line is short: flag = 1 → sell what's left (partial); flag = 0 → sell none of that line. Other lines still sell. `record_sale` returns `(sale_id, shortfalls)` where shortfalls = (medicine_id, requested, sold); sold 0 = left off, 0<sold<requested = partial. Transactional atomicity is unchanged and always holds. **Owner input (2026-08-20):** she GIVES the partial amount (what's in stock) and schedules the patient to come back for the rest when it runs out — so partial selling is her normal behavior. Default therefore set to **1 (allow partial)**; the flag now marks *exceptions* she chooses (a medical call). **Still open:** the walk-in (no-consultation) case. Surfaced a now-confirmed future feature: a "schedule to come back" follow-up / restock-waiting list, tied to the clinical side (only a known patient can be scheduled). |
| 23 | **"Stock" means USABLE (in stock and not expired) everywhere** | Expired medicine is unsellable, so selling (`batches_for`), the stock total (`current_stock`), and low-stock alerts (`low_stock`) all ignore expired batches. One consistent definition of stock ("what we can sell"), and expired units can no longer hide a shortage. Expired lots stay in the `batches` table and appear only in the expiry alert, for disposal. Still open with owner: how to record disposal of expired stock. |
| 28 | **Self-update via GitHub Releases, standard library only** | Author is away most of the year, so the app updates itself: on start it asks GitHub for the latest release, and if newer downloads the exe, verifies SHA-256, and installs it. Uses only urllib/json/hashlib (no dependency). Safe because data lives in Documents\ClinicDB, separate from the program. Chose GitHub Releases (free, clean direct URLs, API needs no auth). Release process in RELEASING.md; version in updater.CURRENT_VERSION must match the release tag. |
| 31 | **UI in English or Thai (toggle); Lao supported as typed text, not UI** | Owner reads Thai; Lao (her language) has poor font/wording support so it's not offered as a UI language, but Lao text stores and displays fine in any field (UTF-8 DB, Leelawadee UI font + system Lao fallback). Localization is via `i18n.t(text)` (English text is the key; missing translations fall back to English) + a saved language in settings.json. GUI translates by walking the built widget tree once (each widget's English original remembered), so most static text needs no per-string wrapping; table headings wrapped with t(). Language dropdown in the status bar; applies on reopen. Thai strings are a DRAFT for the owner/author to review. Dynamic messages and the report stay English for now. |
| 30 | **Record the seller on each sale; report sales by staff** | `sales.employee_id` records who made the sale (optional). A counter sale gets it from a "Sold by" dropdown; a visit sale is attributed to the doctor who saw the patient (visit's employee_id). `reports.sales_by_employee` and a "SALES BY STAFF" section show each staff member's count and revenue. Gives accountability and a simple per-staff contribution view. |
| 29 | **Update installs by rename-in-place + user reopens (NOT auto-relaunch)** | A PyInstaller one-file exe validates the process that launched it; every attempt to auto-relaunch the new exe (direct Popen, `start`, `explorer`) failed that check ("parent process has different executable / failed to obtain parent path"), because those launchers exit immediately. Resolved by NOT relaunching: rename the running exe aside (Windows allows renaming a running exe), move the new one into place, and ask the user to reopen — a normal double-click is the only launch that reliably passes the check. Old exe kept as ClinicSystem-old.exe, deleted by cleanup_old() on the next open. Lesson: shipping the auto-updater means the FIRST version's updater must be correct, or one manual install is needed to get past a broken one. |
| 27 | **Sales record paid vs owed; a debt must belong to a patient in the records** | Owner sometimes lets people pay later. `sales.paid` (1/0) records it; a pay-later sale must be tied to a real patient — via its visit, or `sales.patient_id` for a counter credit sale — so every debt is attributable to someone we can find. `record_sale` refuses an unpaid sale with no patient. Debts are viewed via `outstanding_debts()` and cleared with `mark_sale_paid()`. Also: medicine given in a visit can be marked FREE (a sale line at price 0, reusing the existing per-line price override). |
| 26 | **No calendar widget — typed dates with validation; zero outside dependencies** | Tkinter has no built-in calendar. Options were: install `tkcalendar` (first outside dependency), hand-build one (lots of fiddly code), or keep typed ISO dates with validation. Chose typed dates: the project stays 100% standard-library, which keeps packaging simple and is easy to defend. Revisit only if date-typing proves error-prone in real use. |
| 25 | **Track cost & profit; add `received_quantity` for reorder spend** | Money-out and profit reports need cost data. Cost per source was already modelled: each `batch` has its own `purchase_price` and `supplier_id`, so the same medicine bought from two places = two batches with two costs. Profit is computable because each sold line records `batch_id` → its cost. But `batches.quantity` is the *remaining* amount, so the original purchase size was lost; added `received_quantity` (fixed at receipt) so reorder spend = `received_quantity * purchase_price`. Reports: `financial_summary` (revenue, COGS, gross profit), `reorder_spend` (+ by supplier). Also: seeded sales now use the REAL `record_sale`/`record_visit` (so sample sales set `batch_id` and decrement stock), making the sample data realistic enough for the profit report. |
| 24 | **Price lives in the DB; a sale line may override it (free / discount)** | `medicines.unit_price` is the current catalog price — looked up automatically at sale time, so staff never memorize prices. A sale line can be `(medicine_id, qty)` (use catalog price) or `(medicine_id, qty, price)` to override — e.g. `0` for a free giveaway, or a discount. The price used is frozen onto `sale_items` (decision #4), so changing a catalog price later is a one-line update that never rewrites past receipts. Note in code: test `unit_price is None`, not falsy, so 0 (free) is treated as a real price. |
| 32 | **Replaced the "give medicine free" checkbox with a whole-sale DISCOUNT amount (walk-in AND visit)** | Owner input: instead of only all-or-nothing "free", staff enter a kip amount to deduct (price 15,000, discount 5,000 → charge 10,000). `record_sale` gained a `discount` parameter that lowers the frozen line prices in proportion so the total drops by exactly that amount (`factor = (total − discount) / total`); a discount equal to the total makes the sale free (the old checkbox is now just "enter the full price as the discount"), and it is capped at the total so a sale can never go negative. Because the discount is baked into the frozen `sale_items` prices, every report and the debts view reflect it with **no schema or report changes**. Both panels get a "Discount (₭)" box; `record_visit` passes it straight through to `record_sale`. Free-medicine `visit_free` flag removed. |
